# 2.3.4 识别、布局与多视频验收 · 2026-10-04

## 原始问题与修正

用户 2.3.3 截图中，视频已经显示画面，线路已确认，但播放卡片仍加载；另有页脚/滚动异常、候选仅三个及低播放量最高画质卡顿。

新增失败回归先证实：追踪参数触发假导航、同一个 MSE 播放器只有 playing 而没有第二个 loadedmetadata 时卡在加载、健康监测误选 DOM 前方的预览；修正后通过。主播放器移除不保留旧绑定，重复切换不重复监听。进度长时间停止且没有 waiting 事件时展示“播放停滞”，不把此展示判定反向喂给选路。

实际媒体来源之前主要在 XHR load、fetch 响应或 resource timing 完成后确认，大分段慢/取消时会晚于真实播放请求。2.3.4 在 fetch/XHR send 发出阶段取得实际视频路径及 Range；SSR 通常晚于 document-start 才赋值，增加即时补读和 DOM-ready 观察。请求意图可以确定实际选择的画质，但不设置已确认响应主机；响应与请求仍分离。音频不能覆盖视频源。后台睡眠重启可重放当前请求意图。不是修改 2.2.0 的数值策略。

完整 DASH 描述中后面的备用 host 之前可能被前八个 URL 截断；现保留经校验的视频 host，但始终使用实际视频路径测速。默认仍阿里/腾讯/华为三个、最多八候选，未添加猜测节点。Akamai 作为只读来源可以显示，不测速、不固定、不排除；汇总区分候选和仅观察来源。

界面改为固定 400×600 的纵向框架，页脚不参与外层滚动；候选为独立块级滚动区，避免网格隐式行和动态状态把列表/按钮挤到页脚。列表更新时保持滚动位置，但在可滚动范围缩小时允许正常钳制，不以不可能的旧 scrollTop 为通过标准。

## 测试方法与反例

独立、静音 headless Edge，未打开原生弹窗、未修改用户日常 Edge。顺序播放，不多视频并行抢带宽；禁用浏览器缓存，保留插件正常缓存路径，并专门覆盖一次冷测速。CDN 是否缓存和实时网络不能控制；不能把重复播放的改善全部归功于代码。

`multi-video-start.js` / `multi-video-report.js` 每 250ms 记录播放头、输出帧计数、掉帧、缓冲、seeking、原生事件及实际请求。联合发现没有事件的进度/帧停滞和超过四秒的 seek。HTTP 错误、网络错误与取消分别记录；取消不能一律当无害，也不能一律当服务器故障。没有 waiting/stalled 不足以判定不卡。headless 的解码和播放头观察不证明物理屏幕渲染流畅。

- 第一轮指定视频恢复到 191 秒，只播结尾约 17 秒；该结果作废，不能称整段通过。后续明确从零开始，并保存视频结束时的元数据，避免自动连播污染标题/画质。
- `BV1PCHi6KERb` 初次在本轮打开，约 1,203 播放量，1080P 60 帧。约 100 秒墙钟时间只前进到 33.46 秒：多次 waiting、帧停止、播放头停止、约 12 秒 seek；来源经历腾讯、阿里与 Akamai。206 响应中也出现 5/10 秒后取消。没有把这个失败删除或用别条视频覆盖。跳转从 7.964→8.464 的 +0.5 秒与插件 -0.15 秒回退不同，不能直接归因插件触发；自然网络/播放器因素和完整因果仍未知。
- 同一失败视频在请求阶段识别修正及重启测试配置后再次从零完整播放 105.024 秒，1080P 60 帧，423 次采样、6,301 帧、16 掉帧；中途无检测到的停滞/seek，稳态最低缓冲 10.146 秒。浏览器缓存未命中，但 CDN 温度和网络变化仍混杂，因此这是改善观察，不是严格因果证明。
- 新加入本轮未播放过的 `BV17eHY6yEJm`，约 2,752 播放量，1080P 60 帧，从零完整播放 86.55 秒；367 次采样、5,193 帧、0 掉帧，无中途停滞，稳态最低缓冲 10.016 秒。前三阶段的高画质启动约五秒不能忽略，不能宣传任意时刻瞬间开播。
- `BV1g5t966E1e` 约 2,265 播放量、23 秒短片完成过一次探索，但早期采集器尚未冻结标题，自动连播污染了后读元数据；不纳入最终版本完整验收。
- 指定 `BV1Kwam6FEZZ` 约 9,648 播放量，最高可选档是 1080P 高码率 / 30 帧，不是 60 帧。本轮另一次完整播放从零到 206.786 秒，831 次采样、6,199 帧、0 掉帧，未记录中途停滞，稳态最低缓冲 10.096 秒、浏览器缓存未命中。它属于重播、插件暖缓存组，不当作新样本；另一次清除插件测速缓存的完整播放也成功，但 CDN 仍可能已暖，不用它证明修正造成改善。以上最终有效样本共三个不同视频，重复次数不增加独立样本数。

最后增加的跨页面延迟响应过滤，由单元回归验证；整段播放采集开始早于此过滤补丁，不宣称这些播放已覆盖该最后补丁。完整因果验收仍需用户前台原始线路/自动线路对照，交换顺序、多条新视频，且不能把某条成功覆盖另一条失败。

这是一版识别、候选和布局正确性修复，不是“所有低播放量视频的卡顿已根治”。不能仅凭成功重播将初次失败归因于旧代码。用户前台的实际卡顿根因仍需一致环境的诊断证据。真实 Chrome 独立客户端、iPhone、不同网络/缩放未作全量实机验收。原始用户 2.2.0 ZIP 保留，网站资源由用户指定网站任务独立审核更新。
