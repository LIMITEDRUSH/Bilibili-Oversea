# 2.3.2 基线与发布验收 · 2026-10-04

## 用户确认的范围

固定 2.2.0 的选路策略，保留正确性修复，并逐项验证新增改动。不逐字恢复旧版会被播放重定向污染的测速。保持 2.3 的亮色界面、图标及原生弹窗尺寸修复。个人网站整合没有在本次执行；手机运行逻辑未改动。

基线测试锁定默认候选、吞吐量/首包/原线路排序、128 KiB 初筛、前三名 1 MiB 复测、256 KiB 双节点轻量复核、20% 增益、3 小时成功/10 分钟失败缓存、15 分钟轻量复核、10 秒发现心跳、2 秒健康采样及原有缓冲/冷却阈值。

## 证据与被撤回的方案

目标是用户指定的低播放量视频 `BV1V3Ye6zE6f`，使用用户自行登录的独立 Edge 配置，最高可选档为 1080P 60 帧，实际分辨率 1920×1080，时长约 183.77 秒。没有读取或复制账号、Cookie、密码。

这些不是控制编码、时段与服务端分配的严格 A/B 实验。相同清晰度标签仍可能拿到不同编码/文件大小。两版基线这次都未自然复现用户报告的卡顿，所以不能宣称新版本普遍更快。原先的 Akamai 跨 CDN 方案因真实退化而撤回，不把小块测速成功当成大段视频一定可靠。

保留的改进只涉及识别与测量正确性：区分视频/音频、等待真实画质地址、记录响应 host 和当前 Range 起点、最高画质切换时重新复核、后台唤醒时优先重放视频、源主机覆盖更新及插件恢复 seek 的看门狗。Akamai 只读观察、原始直通，规则和候选均排除它，没有新增主机权限。

## 可重复的长播放复测

在只加载最终 ZIP 的独立 headed Edge 配置中自行登录、选择最高画质；不要使用日常浏览器配置做会修改模式的 QA。

1. `run-code --filename browser-extension/qa/hd-playback-start.js`：退出上一播放、撤销旧任务/规则，开启自动模式并清除专用配置中的旧测试缓存，然后从头播放目标视频。
2. 重复运行 `hd-playback-sample.js`，每次采样 40 秒，期间不要操作播放、进度或弹窗。
3. `hd-playback-report.js`：确认第一条视频完整结束、1920×1080/60 帧、没有中段 waiting/stalled/seek/pause/error；只有满足这些条件才返回 `pass: true`。结尾耗尽缓冲不是网络卡顿，稳态统计排除开头与结尾各 10 秒。
4. 完整播放结束后才运行 `real-popup-check.js`、`probe-routing-check.js`，不要把控制测试插入连续播放验收。Akamai 时路由脚本使用明确标记的受控隔离规则样例，测试结束删除；不会自动把 Akamai 视频改道。

报告冻结第一条视频结束时的画质、分辨率与帧计数，网络统计只包含结束前的请求，避免自动下一视频混入结果。报告不打印签名、完整媒体 URL 或登录信息。暖缓存复测可在 start 前设 `page.__lowplayCacheMode='warm'`，保留专用配置缓存；原始对照设 `page.__lowplayMode='original'`。

## 边界

本次没有真实手机、Chrome 独立浏览器、付费番剧、所有分辨率与弱网组合的实机验收。单视频通过不能证明所有网络、所有视频永不卡顿。Akamai 保留平台原始播放，不承诺对其强制改道或自动救援。缓存再快也不能解决断网、总带宽不足或服务端拒绝。
